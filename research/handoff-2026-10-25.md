## How live data is obtained (reflash-free)

Root over UART, start `telnetd -l /bin/sh -p 2323` for a network shell, then use the
pure-Python TCPROS toolkit in [scripts/](../scripts/README.md). The robot's rospy is
incomplete, so the tools speak raw TCPROS (stdlib only). Key calls:
- Map: service `/map/GetCurrentCompressMap` (type=0, mapid=0, md5 `*`)
- Robot pose + state: topic `/robot/Robot`
- Map origin: `slam/SlamMap` metadata
- Charger: service `/map/ManipulateCharger`

## Key technical facts

### Map (map/CompressMap)

- Response = `uint8 result` + CompressMap: `uint32 mapid`, `MapMetaInfo` (mapWidth, mapHeight,
  cols, rows, submapWidth, submapHeight, resolution-mm), `CompressSubMap[]`.
- Tiled: cols x rows submaps, row-major. Each submap data = LZMA1 "alone" with an Ecovacs
  truncated 8-byte header (reinsert 4 zero bytes after byte 8). One byte per cell.
- Live map is 8x8 tiles of 100x100 (= 800x800 @ 50 mm). Cell values: 0 unexplored, 2 wall,
  5 obstacle, 4 unsegmented floor, 101..109 room segments.

### Coordinate transform (world to grid), validated for the robot

- Units: poses are **mm**, theta **radians**. Dock is the SLAM origin.
- SLAM grid is 1200x1200 @ 50 mm centered on world origin; the CompressMap is the center
  800x800 window, so **world (0,0) = grid pixel (400,400)** (mapWidth/2, mapHeight/2).
- `grid_x = width/2 + x_mm/resolution_mm`, `grid_y = height/2 + y_mm/resolution_mm` (**no y-flip**).
- Heading **theta=0 points down** (grid +y); Valetudo angle (0 = up) = `180 + deg(theta)`.
- Valetudo entity point (cm) = grid_pixel * pixelSize_cm; pixelSize = resolution_mm / 10 = 5.
- Caveat: carrying the robot by hand delocalizes it; pose is only trustworthy when the robot
  localizes itself. The charger's stored pose is wiped on pickup (returned 0,0 once).

### /robot/Robot state message

Fields: Header, PredictPose (two Pose = Header + x,y,theta), power/Battery (uint8 battery,
uint8 lowVoltage), power/ChargeState (uint8 isOnCharger, uint8 chargeState), then
motor currents, range detects, onOffInfo[], bump[], downin, fall, dirtbox, carpet, waterbox,
ldsPic. Battery + charge are parsed (fixed offset after the two poses). Attachments sit after
the variable-length arrays , see "next steps".

## UPDATE 2026-10-26: DEPLOYED, RUNNING, AND (almost) LINKED TO HOME ASSISTANT

The reflash and on-device backend are DONE. The fork now runs fully local on the robot.

**Flashed.** The modified rootfs was written in place from uboot (ubi write, crc32-verified).
`/etc/rc.local` starts the backend on every boot and brings up persistent telnet on 2323, so
UART is no longer needed for normal use. Backend updates are brick-free: rc.local prefers
`/data/valetudo` over the baked binary, so a new build is just an `nc` copy + reboot (no reflash).

**Running.** The backend serves the Valetudo web UI/API on port 80 over the LAN (robot
192.168.1.93), reads live state from the ROS link (battery, dustbin/water/mop attachment,
status; 9 control capabilities), and is stable across idle + API load and across reboot.

**Three kernel-4.14 runtime fixes were required** (details in deploy/RUNBOOK.md; committed to
the fork as 9f0c42fb):
1. Node 20/22's V8 crashes at startup (no MAP_FIXED_NOREPLACE). Build with **Node 18**.
2. Node 18 can't require() ESM -> pinned crc 3.8.0 / express-rate-limit 6.11.2 / jstoxml 2.2.2;
   added lzma/src/lzma_worker.js to pkg assets.
3. Node 18's V8 still crashes returning memory (madvise(MADV_DONTNEED) fails on this kernel).
   Fix = **deploy/patch_madvise.py** (rewrites the one libc madvise stub to force return 0).
   Build flag also includes no-memory-reducer.

**Config seed gotcha:** the first-boot seed MUST be a full valid config (incl.
webserver.basicAuth) or Valetudo rewrites it with defaults and drops the ROS
implementationSpecificConfig, making Ecocloud TLS fatal. deploy/valetudo_config.seed.json fixed.

**Home Assistant linking (partial, 2026-10-26):** HA host = 192.168.1.100, Mosquitto add-on
(core_mosquitto) started + MQTT integration loaded (both confirmed via the HA MCP, read-only).
Valetudo MQTT was staged via its REST API (PUT /api/v2/valetudo/config/interfaces/mqtt):
host 192.168.1.100, port 1883, identifier ecovacs-x1, topicPrefix valetudo, credentials
section enabled, MQTT still disabled. REMAINING: set an MQTT username+password and flip enabled
(the Mosquitto add-on accepts an HA user login or a dedicated add-on `logins` user; no anonymous).
There is no Valetudo MCP server; Valetudo is driven over its HTTP REST API. HA autodiscovery is
automatic once MQTT connects, so the vacuum entity appears with no HA-side config.
